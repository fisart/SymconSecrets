# Security audit remediation and production transition

Scope: the 4 November 2026 audit of SymconSecrets, applied to the current native-only replacement. This update is prepared on `fix/security-audit-production`, based on installed migration build 8. It is not a declaration that live installation acceptance is complete.

## Before installing this branch

The frontend accepts Symcon's own SSL listener even when the embedded PHP request has no `HTTPS` flag. It first checks an engine-identified active WebServer caller. On Linux and Docker, where module hooks can omit that caller, it matches the actual request's engine-supplied remote IP and source port to one established kernel TCP connection in the current network namespace. Its local address/port must belong to one active, applied, SSL-enabled Symcon WebServer. Build 14 also handles hooks that omit the client source port or report the destination port instead: every possible live connection from that peer must map to an active SSL listener. A concurrent unknown/plain connection, including a client-half-closed CLOSE_WAIT request, refuses that fallback; an exact SSL tuple can still be used independently. External NAT ports need not equal the internal SSL port. No certificates, private keys, complete WebServer configurations, infrastructure settings or trust roots are read or changed by this detection. No subprocess, outbound request or extra service is used.

This is request binding, not a search for any SSL listener: another port/address, a plain listener, unapplied settings or unavailable peer/kernel evidence do not establish trust. Generic embedded-PHP HTTP flags do not override a kernel-bound SSL connection. Without an exact client tuple, mixed SSL/plain candidates remain unverified. Host, Origin and arbitrary forwarding headers cannot qualify a plain listener. Existing explicit HTTPS flags, exact trusted proxy evidence and the narrowly qualified Magic relay remain supported. On platforms without Linux kernel tables, engine caller evidence or the existing explicit TLS/proxy/relay evidence is required. A browser certificate display alone still cannot establish which internal listener accepted the request.

Build 13 adds native listener recognition and build 14 extends it to incomplete Symcon hook metadata to the existing transport check. Install it from `migration/legacy-sec-replacement`, reload the normal HTTPS address and sign in. No infrastructure or certificate change is required for this module update. Live recognition still needs confirmation on the installation; the regression tests bind real loopback kernel connections and verify listener selection, not a live Heartbeat login. If recognition is unavailable the request remains refused and the approved Magic route remains available. The refusal includes safe listener observations (caller ID, whether a remote address was supplied, the reported port and kernel-table readability); no cookies, addresses, certificate/key files or secret values are exposed. The prior YE2 chain-completion implementation and strict peer certificate/hostname validation are unchanged.

Build 15 removes the optional `SERVER_ADDR` prefilter: that field may describe an external/NAT address and is not needed for peer-tuple uniqueness or kernel-local SSL bind matching. Missing-source-port candidates now include all local addresses, so reported server metadata cannot hide a concurrent plaintext connection. Refusal diagnostics enumerate at most eight redacted candidate ports and applied SSL listener IDs/port types/bind categories, plus exact/peer tuple counts and a reason code. Other-client addresses, certificates, cookies and keys are never included. A later diagnostic snapshot can observe a different state from the refused request and is explicitly labelled accordingly. This release does not claim to have reproduced the remaining live Heartbeat mismatch; its expanded observation is intended to identify it if the NAT correction does not resolve it.

Build 16 corrects IPv4 wildcard matching for IPv4-mapped IPv6 sockets. Linux can put the accepted socket in `tcp6` while Symcon's applied listener bind remains `0.0.0.0`. The IPv4 wildcard now checks the normalized local address family; an IPv6 wildcard still checks its IPv6 socket family. A pure IPv6 address is not accepted by an unrelated IPv4 wildcard. The regression fails against build 15, then passes after the change. It also creates five real concurrent dual-stack loopback connections and confirms kernel family 6, normalized address family 4, exact peer matching, SSL-only fallback and plain-listener refusal. Diagnostic entries now distinguish kernel storage `family` from normalized `addressFamily`. Native authentication, Magic and configuration-backup checks also pass. Live Heartbeat sign-in remains to be confirmed after installing the update.

## Production application writes

The vault's normal administrator writes and shared Global history are separate from the old SEC compatibility-write freeze. In **Automation access → Production application access**, **Enable production writes** prepares an exact `nativeLegacyAccess` approval for this installation's detected backend. Confirm with the administrator passkey (or hardware key if required by policy). It enables ordinary application writes and clears the compatibility freeze, while retaining current read, bulk-replacement and protected-page permissions. Repeat on each installation that needs application writes. Review explicitly disabled grants before enabling them.

The same **Enable production writes** approval is also available in **Mailbox → this server → Production application writes**. Both locations use the existing exact passkey approval and the same saved grant. The Mailbox entry becomes Completed after approval and is hidden by its default outstanding filter; it returns if writes are subsequently disabled or frozen. Each installation offers its own local approval; remote approval authority is not extended. The local administration entry is not added to signed mesh summaries, keeping those reports compatible with older peers.

The header displays **Production system** only when the saved local grant enables unfrozen application writes. Otherwise it says **Secrets system**. Installation of code alone does not change an existing permission or grant itself authority. No ownership-transfer freeze, disabled grant on another installation, pending synchronization or hardware enforcement is overridden.

## Backups and acceptance

Configuration backup and complete encrypted vault backup serve different purposes. Before production activation, verify a current encrypted vault package and separately retained recovery key and perform a restore rehearsal on a disposable installation. Keep configuration backups as well. Native Global replication is asynchronous: a matching health check is a matching observation at that time, not a quorum commit, linearizable read, or independent rollback guarantee.

Software regression evidence is recorded with the release. Physical keys, actual proxy/Connect behavior, primary-certificate outage, filesystem/power-loss behavior and real-provider idempotency cannot be certified by synthetic tests. Complete those installation-specific checks before closing the audit or claiming unrestricted production readiness.

No configuration export schema change is required. Grants retain the existing versioned configuration format; recovery outcome identifiers and rejection sampling are runtime bookkeeping. No external database, service or runtime dependency is introduced.

## Executed regression evidence

The native test suite passed with supplied OpenSSL/Sodium, no database drivers and a 32 MiB PHP limit. All 19 browser test scripts passed. Added regressions exercise enforced-profile refusal through both native and general configuration review/commit paths; 3,499/3,500 and 4,112 retention boundaries; bounded recovery history; actual encrypted-backup compaction with interruption before and after publication; rejection-flood journal publication counts; encrypted Local recovery of all conflict variants with authority unchanged; and a three-vault OAuth partition with a single Local refresh executor. An authenticated HTTP reveal carrying a valid cookie/CSRF token and forged forwarding evidence is refused without exposing values. Existing full Magic synthetic tests still pass.

The read-load check retained 120 snapshot loads and zero writes for 30 application-read cycles. Signed discovery/health/mesh receiver checks retained two loads per response; only HELLO's existing admission rate record writes. Configuration export/import validation and isolated restores passed. These are local regressions, not live deployment or independent security certification.


## Automated acceptance checks (build 10)

`Native production acceptance` runs on relevant pushes and pull requests. It runs the complete database-free native/fault suite and every browser regression, then retains logs and a commit-bound JSON summary for 30 days. The summary always marks live deployment, physical keys, real Magic outage login and externally saved-backup restore as not tested. The workflow also supports dispatch where GitHub exposes it; existing runs can be rerun from Actions. These tests use disposable synthetic fixtures and never receive production credentials or vault files.

In **Encrypted backup → Automated production checks → Run automated checks**, one export-class passkey approval runs a bounded encrypted-backup round trip on the current installation, validates its Global/Local values and identity, and prepares a separate recovery representation in memory. No values are restored into the live vault. The server also reports storage/retention headroom, current eligible hardware configuration, and saved authenticated synchronization/primary/backup observations. Its result contains no secret values, recovery key or encrypted package. The current request's HTTPS evidence is appended by the Symcon frontend. The page only displays the server results.

This checks recovery software against the current snapshot. It does not verify the user's separately retained backup file/key, boot a fresh installation, disable a primary endpoint or perform a physical key touch. Those remain explicit not-tested rows. Memory or missing observations are reported as not tested/attention; they cannot turn into a production-acceptance certificate. Console access remains an independent recovery path, and reverting code does not undo secret edits or permission changes.
